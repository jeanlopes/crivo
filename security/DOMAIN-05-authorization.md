# Domain 5 — Authorization and tenant isolation

Broken access control is first in the OWASP Top 10 (2025) and the most common way a SaaS leaks one customer's data to another. Scanners barely see it: the code is syntactically fine, it just forgot to ask *whose* record this is. That is why this domain leans on tests the human specifies, not on tools.

---

### SEC-057 · Deny by default and decide authorization in one place
`ASVS:V8` `CWE-285` `CWE-862` `T10:A01` · verify: sast, test · severity: critical

Every handler calls an explicit policy check before touching data; a handler with no check is a failure of the route-manifest test (SEC-035), not a public endpoint. Policy lives in one module that can be tested as a table, not in `if` statements scattered through controllers.

### SEC-058 · Check object ownership on every access by identifier
`ASVS:V8` `CWE-639` `API:API1` `T10:A01` · verify: abuse · severity: critical

Broken object-level authorization (BOLA/IDOR): `GET /invoices/1043` returns invoice 1043 to anyone who asks. Queries filter by the caller's tenant and ownership, not only by ID. Random UUIDs make enumeration harder but are never the control — IDs leak through URLs, logs and shared links. Parler (2021) was scraped through sequential IDs with no rate limit. Test: the authorization matrix (SEC-062) runs every object route as a second user and a second tenant and expects 404 or 403.

### SEC-059 · Check function-level authorization on privileged operations
`ASVS:V8` `CWE-285` `API:API5` · verify: abuse · severity: critical

Admin and manager endpoints verify role or permission, not only that the caller is logged in. Hiding a button in the UI is not authorization.

### SEC-060 · Authorize individual properties on read and on write
`ASVS:V8` `CWE-213` `CWE-915` `API:API3` · verify: test · severity: high

Responses serialize only the fields the caller may see (no `passwordHash`, internal notes, other users' emails in a list response); writes accept only the fields the caller may set (SEC-009).

### SEC-061 · Enforce tenant isolation in the data layer as well as in code
`ASVS:V8` `CWE-639` `T10:A01` · verify: config, test · severity: critical

Postgres Row-Level Security keyed on the tenant, per-tenant schemas or databases, or storage security rules, so that a missing check in application code fails closed. For Backend-as-a-Service stacks (Supabase, Firebase) where the browser talks to the database directly, the security rules *are* the authorization layer: a table without RLS is public. In 2025 many applications generated by an AI app builder exposed their data because RLS was never enabled (CVE-2025-48757). Test: a query run with a tenant-A session against tenant-B rows returns nothing.

### SEC-062 · Specify authorization as a matrix and test every cell, including the forbidden ones
`ASVS:V8` `CWE-285` `T10:A01` · verify: abuse · severity: critical

`spec/security/authz-matrix` lists role × resource × action → allow/deny, including anonymous, another user of the same tenant, and a user of another tenant. The gauntlet generates or requires one test per cell. Negative cells are the point: most authorization bugs are an *allow* nobody wrote down.

### SEC-063 · Never trust the client for anything that matters
`ASVS:V2` `ASVS:V8` `CWE-602` · verify: adversary, abuse · severity: critical

Prices, discounts, roles, feature flags, "current user ID", hidden form fields, disabled buttons and client-side route guards are all attacker-controlled. The server recomputes or re-reads them.

### SEC-064 · Give every identity the least privilege it needs
`ASVS:V13` `CWE-250` `CWE-269` · verify: iac, config · severity: high

The application's database user has no DDL and no superuser rights; each service has its own credentials; cloud roles are scoped to named resources and actions; read paths use read-only credentials where possible. Least privilege is what turns a breach of one component into a breach of one component.

### SEC-065 · Authorize on every entry point, not only on HTTP
`ASVS:V8` `CWE-862` · verify: test, adversary · severity: high

Background jobs, queue consumers, websocket messages, GraphQL field resolvers, file downloads, exports, email-reply handlers and scheduled tasks re-check permission at the time they act, for the user they act on behalf of — permissions may have changed since the job was enqueued.

### SEC-066 · Make signed URLs short-lived and narrowly scoped
`ASVS:V8` `CWE-284` · verify: test · severity: medium

Pre-signed storage and download URLs are bearer credentials: one object, one method, minutes of validity, and generated only after an authorization check.

### SEC-067 · Verify every inbound webhook
`ASVS:V4` `CWE-345` · verify: test · severity: high

HMAC signature over the raw body with a per-integration secret, constant-time comparison, a timestamp inside a short window, and replay protection by event ID. An unverified webhook endpoint is an unauthenticated write API.
